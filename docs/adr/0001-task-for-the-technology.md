# 0001. Задача под технологию: очередь заданий

## Контекст

Проект учебный: цель — разобрать RabbitMQ на практике. Поэтому
задача подбиралась под технологию.

Профиль брокера, который хотелось задействовать целиком: длинная работа вне HTTP-запроса,
подтверждение по каждому сообщению, повторы и очередь ошибок без своего планировщика, веерная
рассылка одного события в независимые каналы, отсутствие потолка на число обработчиков.

Реальная нагрузка такого стенда — десяток запросов в день. Под неё не нужен брокер.

## Варианты

1. **Выгрузка исторической погоды по запросу** — выбрано: единица работы это поручение, оно живёт
   минуты, выполняется одним исполнителем из пула и после обработки исчезает.
2. **Поток телеметрии** — уже сделан в парном
   [MeteoStream.Kafka](https://github.com/DevCorvette/MeteoStream.Kafka): это форма журнала,
   а не очереди, и разбирать на ней Rabbit значило бы бороться с инструментом.
3. **Проектировать под настоящую нагрузку этого стенда** — тогда не нужен брокер и проект
   теряет смысл.

## Решение

Сервис асинхронной выгрузки: клиент заказывает погоду по списку точек и диапазону дат, работа
уходит в очередь, воркер собирает CSV, по завершении уходят письмо и вебхук.

**Работа обязана быть честно долгой.** Полсотни точек за десять лет почасово — это десятки вызовов
API и мегабайты CSV, то есть минуты. На секундной задаче вся конструкция с очередями выглядела бы
избыточной, а половина механики не проявилась бы вовсе.

## Последствия

- Всё проверяется на минутной работе: `consumer_timeout`, видимый прогресс, повторы,
  идемпотентность обработчика — это настоящие проблемы, а не упражнения.
- Брокер оправдан формой задачи, а не нагрузкой: под настоящую хватило бы очереди в PostgreSQL
  и уведомлений внутри воркера ([ADR-0002](0002-transport-choice.md)).
- Цифры нагрузки вымышленные. При настоящей нагрузке пул воркеров, кворумные очереди
  и приоритеты по классам размера простаивают.
