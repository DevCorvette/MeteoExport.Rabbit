# MeteoExport.Rabbit

[![build](https://github.com/DevCorvette/MeteoExport.Rabbit/actions/workflows/build.yml/badge.svg)](https://github.com/DevCorvette/MeteoExport.Rabbit/actions/workflows/build.yml)

Сервис асинхронной выгрузки исторической погоды: клиент по HTTP заказывает данные по списку точек
и диапазону дат, работа уходит в очередь, воркер собирает CSV в объектное хранилище, по завершении
клиент узнаёт об этом письмом и вебхуком.

Проект учебный: цель — разобрать RabbitMQ на практике, поэтому задача подбиралась под технологию.
Под настоящую нагрузку такого стенда — десяток запросов в день — хватило бы двух сервисов:
API и воркера с очередью заданий в PostgreSQL, письмо и вебхук ушли бы внутрь воркера, а брокер
не понадобился бы вовсе. Здесь он оправдан формой задачи, а не нагрузкой.

.NET 10, ASP.NET Core, MassTransit 8, RabbitMQ 4, PostgreSQL 17, EF Core, MinIO, MailKit, RestSharp,
NLog, Docker Compose.

## Запуск

```bash
docker compose up -d --wait
```

Поднимает PostgreSQL на `localhost:5434`, RabbitMQ на `localhost:5672` с UI на
[localhost:15672](http://localhost:15672), MinIO на `localhost:9000` с консолью на
[localhost:9001](http://localhost:9001) и mailpit — smtp на `localhost:1025`, ящик на
[localhost:8025](http://localhost:8025). Логин и пароль у базы, брокера и хранилища — `meteoexport`.

```bash
dotnet run --project src/Corvette.MeteoExport.Migrator
dotnet run --project src/Corvette.MeteoExport.Api
dotnet run --project src/Corvette.MeteoExport.Worker
dotnet run --project src/Corvette.MeteoExport.Notifier
```

Мигратор отрабатывает и завершается, остальные три — долгоживущие процессы, работают одновременно.
Схема API — на [localhost:5080/scalar](http://localhost:5080/scalar).

```bash
curl -X POST http://localhost:5080/exports -H "Content-Type: application/json" -d '{"points":[{"latitude":55.75,"longitude":37.62,"name":"Москва"}],"from":"2020-01-01","to":"2020-12-31","variables":["temperature_2m"],"email":"user@example.com"}'
```

В ответ приходит `jobId`; дальше `GET /exports/{id}` показывает прогресс, а по завершении отдаёт
ссылку на файл, и письмо о том же самом лежит в ящике mailpit.

```bash
dotnet test
```

Тестам не нужны ни база, ни брокер, ни сеть: под ними валидация запроса, канонизация и отпечаток,
сборка ответа о статусе.

## HTTP

| Ручка                     | Что делает                                                          |
| ------------------------- | ------------------------------------------------------------------- |
| `POST /exports`           | Принимает запрос, отвечает `202` и `jobId`; повтор не создаёт второе задание |
| `GET /exports/{id}`       | Статус, прогресс, текст ошибки, ссылка на файл у завершённого       |
| `GET /exports/{id}/file`  | Сам CSV; `409`, если файла у задания нет                            |

## Очереди

```
exchange exports                          → queue exports         команда «выполнить», N воркеров, prefetch=1
exchange …:FinishExportMessage            → queue exports.finish  подвести итог: инбокс + аутбокс, миллисекунды
exchange MassTransit:Fault…               → queue exports.fault   ставит Failed после исчерпания повторов
exchange …:ExportFinishedMessage          → queue notify.email    письмо, свои повторы и свой notify.email_error
                                          → queue notify.webhook  вебхук, свои повторы и свой notify.webhook_error
```

Очереди кворумные, у каждой точки приёма своя `_error`.

## Архитектурные решения

Разобраны по одному в [`docs/adr`](docs/adr): контекст, варианты, цена.
Остальное коротко:

- Команда адресуется в обменник (`exchange:exports`), событие публикуется в обменник по типу.
  Отправитель не указывает очередь: адрес `queue:exports` заставил бы его объявить и её тоже.
- Повторы `UseMessageRetry` идут внутри процесса, пауза выдерживается в памяти.
- `consumer_timeout` поднят до двух часов переменной окружения прямо в `docker-compose.yaml`:
  задание идёт минутами, а по умолчанию брокер закрывает канал через тридцать.
- Доставка at-least-once во всех трёх потоках. Дубли ловятся захватом задания, инбоксом финализатора
  и `X-Delivery-Id` на стороне получателя вебхука.
- Приоритеты, если понадобятся, — разными очередями по классам размера (`exports.small`,
  `exports.large`), а не `x-max-priority`.

## Особенности

- Кусок работы — пачка точек за отрезок дат, то есть ровно один запрос в Open-Meteo: 25 точек
  и 365 суток.
- Прогресс пишется в базу не чаще раза в десять секунд.
- Координаты в файл пишутся заказанные, а не пришедшие: в ответе они подтянуты к узлу сетки,
  и у двух близких точек совпали бы.
- Значения переносятся в CSV сырым текстом числа, без разбора в `double`: лишний разбор с печатью
  только исказил бы последний знак.
- Архив Open-Meteo отстаёт от сегодняшнего дня на несколько суток — валидация об этом знает
  и свежие даты не пропускает.

## Уведомления

- Письмо и вебхук читают одно событие, но каждый из своей очереди: лежащий часами эндпоинт клиента
  никак не мешает почте.
- Вебхук — `POST` с JSON и заголовком `X-Delivery-Id`, по нему получатель отбрасывает дубли.
  Идентификатор берётся из `MessageId`, поэтому у повтора он тот же.
- При `Email.Enabled=false` письмо только пишется в лог — сервис проверяется целиком, не требуя
  ни SMTP, ни ящика.

## Настройки

- `appsettings.json` рядом с приложением, локальные переопределения — в `appsettings.local.json`
  (в репозиторий не попадает).

## Осознанно не сделано

- Разбиение задания на куски-сообщения с агрегацией завершения — правильное решение для заданий
  длиннее `consumer_timeout`, но это уже сага, а не очередь.
- Подпись тела вебхука и журнал доставок: и то и другое требует регистрации клиентов, которой нет.
- Аутентификация, мультиарендность, exactly-once.
- Интеграционные тесты с Testcontainers: сейчас тесты не поднимают ничего.
